# smi-mapper
## Описание сервиса:

Сервис smi-mapper предоставляет возможность создания карты источника для ее последующей обработки сервисами smi-collector и smi-parser


Парсинг новостей состоит из 2х этапов которые работают в бесконечном цикле, постоянно добавляя в базу новые новости источника: 

Collector - на этом этапе имея ссылку на страницу с новостями и *карту источника собираются 2 обязательных параметра (ссылка на новость и заголовок) и один опциональный (дата публикации)
Parser - на этом этапе имея ссылку на новость собранную коллектором и *карту источника, собирается тело новости (текст новости, цитаты, ссылки на картинки, ссылки на видео, ссылки на telegram посты и дата публикации если она не была найдена на этапе коллектора)

Карта источника - это набор правил для коллектора\парсера, а так же набор адресов элементов html разметки которые будут использованы или проигнорированы при сборке как тела новости на этапе парсинга, так и параметров на этапе коллектора. Собирается она отдельным этапом единожды, после чего хранится в базе вместе с остальными обязательными полями источника (feed_id, user_id, url).

За этап сборки карты источника отвечает сервис add_map:

Сборка карты для коллектора

Поиск rss источника. Если rss найден, то карта для коллектора не требуется
Если rss не найден, то аддмапер находит все элементы имеющие ссылку, дату и текст на каждой из целевых страниц источника (https://hostисточника/news, https://hostисточника/articles и т.д), затем из них выбирается страница с наибольшим количеством подходящих элементов  - collect_url,  адреса подходящих элементов - collect_elements (кол-во этих элементов не ограничено), а так же паттерн наиболее часто встречающихся ссылок в целевых элементах - link_pattern (нужен для того чтобы этап коллектора проходили только новости)
Если ни на одной из целевых страниц не получилось найти достаточное кол-во подходящих элементов (новостей), то аддмапер соберет все элементы имеющие текст и ссылки, затем найдет самый распространненный паттерн ссылок. в карту при этом войдут:  collect_url - страница на которой было найдено наибольшее кол-во подходящих элементов, collect_elements - адреса всех элементов в html разметке которые содержат ссылки подходящие под найденный паттерн и текст, а так же link_pattern. Так как при этом на этапе коллектора не получилось найти дату публикации новости, аддмапер попытается найти ее на странице новости. Если и на странице с новостью дату публикации так же не удалось найти, то сборка карты считается не удачной, так как дата публикации является обязательным параметром
Сборка карты для парсера
Имея карту коллектора, а следовательно ссылки на новости источника, аддмапер получает html каждой страницы с новостью, затем разбирает их на элементы имеющие любой текст, затем оставляет только те элементы, которые содержат текст встречающийся единожды, затем определяет самый нижний элемент внутри которого находится максимальное количество элементов с уникальным текстом (далее - зона видимости)
Внутри зоны видимости собираются все текста, затем аддмапер находит всех родителей текстового элемента заканчивая самым верхним в зоне видимости
Для каждого из родителей найденных в большей части новостей определяются 14 параметров в число которых входят:
1 - общее кол-во текстовых элементов 
2 - общее кол-во гиперссылок 
3 - общее кол-во медиа 
4 - процент уникальности структурного паттерна ( к примеру  если в 10 новостях аддммапер нашел элемент X внутри которого в 8/10 новостей есть только тег <p> и тег <a>, а в 2/10 новостей только тег <p>, то из 10 элементов с ункальной структурой будут только 2, а значит 20% уникальности структурного паттерна)
5 - процент уникальности текстового паттерна (аддмапер собирает весь текст из элемента, затем векторизует его и получает процент уникальности по аналогии с параметром 4)
6 - средний уровень вложенности (на сколько в далеко от верхнего элемента в зоне видимости находится данный элемент)
7 -  сколько раз в среднем этот элемент встречается в новости
8 - 14 эти же параметры, но усредненные для каждого из элементов
На основе вышеперечисленных параметов, аддмапер используя обученную модель класифицирует каждый из элементов (тело новости\мусор)

Из элементов определенных моделью как тело новости в news_elements входит только самый нижний (самый удаленный от верхнего элемента в зоне видимости), в то время как в trash_items[trash_elements] входят все элементы из тех, что модель определила как мусор
Имея news_elements и trash_items[trash_elements], аддмапер прогоняет каждую новость через парсер получая на выходе собранное тело новости raw_items
Текстовые элементы встречающиеся чаще чем в 40% новостей попадают в trash_items[trash_text_items], картинки\видео встречающиеся чаще чем в 40% новостей попадают в trash_items[trash_text_items]
В карту добавляются опциональные элементы:
div_white_list - список адресов элементов которые не являются текстовыми, но все равно должны быть спаршены как текст. Распространяется только на элементы внутри области видимости 
split_br_tags - если true разделяет текст на абзацы по тегам <br>, если false игнорирует теги. По умолчанию true
dont_get_header_img - если true собирает картинку из мета контента страницы, если false игнорирует ее. По умолчанию true
breaker_items - список адресов элементов встретив которые нужно остановить парсинг
get_all_iframe - если true парсит все теги iframe, если false только те которые имеют <video> внутри. По умолчанию false

## Как поднять

1. Сначала вам нужно создать файл config.ini на основе config_template.ini.
2. Далее вам нужно создать bash-скрипт для загрузки, сборки и запуска проекта.
```
#!/bin/sh
export PRJ=smi-media-produser
mkdir $PRJ
cd $PRJ
git clone ... YOUR PROJECT smi-media-produser
cp ~/config.ini ./src/config/
docker build --no-cache -t "$PRJ" .
docker stop $PRJ"_running"
docker rm $PRJ"_running"
docker run -d --name $PRJ"_running" --restart unless-stopped --network host -e TZ=$(cat /etc/timezone) $PRJ
docker logs $PRJ"_running" -f
```

3. Запустите скрипт bash для загрузки, сборки и запуска проекта.

## Проверка работы сервиса

1. Основной метод проверики работоспособности сервиса (метрики):
```
   1.1. host:5000/api/health/live (Healthy - сервис работает; Unhealthy - сервис не работает)
   1.2. host:5000/api/health/readiness (Healthy - есть доступ в базу; Unhealthy - нет доступа в базу)
   1.3. host:5000/metrics:
      1.3.1. smi_media_produser_healthcheck {"healthcheck": "arangodb"}, 2 - база доступна
      1.3.2. smi_media_produser_healthcheck {"healthcheck": "arangodb"}, 1 - деградация базы
      1.3.3. smi_media_produser_healthcheck {"healthcheck": "arangodb"}, 0 - нет доступа в базу
      1.3.4. smi_media_produser_events, number - кол-во отправленных сообщений 
```
2. Дополнительный метод проверки работоспособности сервиса:
```
   2.1. Проверка статусов новостей в базе (последняя дата и время обработки новостей):

RETURN DATE_ISO8601(MAX(FOR u in smi_items RETURN u.create_date)*1000)

   2.2. Проверка кол-ва каналов в обработке:

for doc in smi_items
    filter doc.status_send_media == 2
    collect with count into len
    return len
```
